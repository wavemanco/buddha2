# Proposed amendment AM-1: separate payload safeguards from financial reservations

Status: **proposal only; not accepted, implemented or authorized for calls**. This is the preferred next decision from the completed specification 0.14 feasibility gate. The checkpoint's no-go remains in force until an amendment is reviewed and its acceptance evidence exists.

The current policy conflates two different controls: limiting a request's measurable size and reserving enough money for everything the provider might bill. A local byte count cannot certify the latter as an 8k/64k provider-token limit. AM-1 keeps the existing scientific request bodies and separates those controls explicitly.

## Exact proposed change

1. Retain the current pre-dispatch payload acceptance sets: canonical UTF-8 request JSON must be at most **5,952 bytes** for answer/plan/quality and **61,952 bytes** for rank/group. These are exactly the current 8,000/64,000 thresholds minus the 2,048 allowance. Name them payload safeguards, not token bounds. Do not enlarge the set of admitted requests, truncate a prompt, or replace a rejected task.
2. Remove the unsupported promise that these byte thresholds enforce 8,000/64,000 provider input tokens. Record actual provider tokens separately when available. This is an explicit control-policy change requiring review, not a corrected estimate under the old policy.
3. For each exact model, endpoint and billing profile, require primary-source support for a maximum **billable input** envelope `M`. A model context-window number alone is insufficient unless its relationship to all billed input, including hidden/schema content, is defensible. If `M` cannot be supported, keep that role blocked; do not substitute another guessed margin.
4. Reserve independently of payload size: `ceil(M * highest_applicable_input_rate + O * highest_applicable_output_rate)`, using integer monetary units and correct units per million. `O` is the transmitted total-output cap (4,096 Sonnet or 16,000 Opus) or documented model maximum (128,000 Luna, because the native body omits a cap). Use the highest applicable ordinary/read/write input rate and all applicable context/service/region modifiers. Never assume a cache hit. For Luna, an envelope crossing its documented 272k threshold must consider the higher full-request rates; it cannot reuse short-context rates simply because the local payload is small. A finite output bound is not itself evidence of a finite billable-input bound.
5. Normalize the exact endpoint's actual usage without losing cache-write categories in the pinned SDK path. Reserve before dispatch, settle only understood categories, retain liabilities for unknown delivery/usage, serialize phase-wide, and preserve zero retry/fallback/repair. Unexpected rates/categories or liabilities halt the phase. Reject missing proof or unsupported profiles before sending anything.
6. Recompute the first-block/full-study financial envelopes and propose a separately reviewed cap. The existing $5/$125 figures are not grants. A conservative reservation could exceed $5 for a single quality request; no new dollar ceiling or completion promise is made here.

The [Luna model documentation](https://developers.openai.com/api/docs/models/gpt-5.6-luna) describes the output maximum, context pricing threshold and write premium. Those facts motivate the amendment; they do not prove a universal `M`. [Anthropic structured-output documentation](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) describes injected billable instructions. AM-1 must account for this content rather than equate visible JSON with model input.

## Bounded scope and acceptance before any use

If approved as a future offline slice, change only admission/accounting definitions and their narrow integration. Preserve tasks, ordering, A/B/C prompts and schemas, role models, reasoning settings, native API routes and metric arithmetic, output caps, human optionality and failure denominators. No provider counting, model listing, auth probes, inference, new strategies, benchmark changes, model upgrades, full-pilot runner or new provider gateway is included. API budget remains $0 for that offline slice; its implementation/time definition must be refreshed before starting.

Acceptance must establish every role's `M` and price modifiers from named sources, independently verify worst-case reservation/settlement arithmetic, test the unchanged payload acceptance set, and exercise the actual pinned SDK against mock HTTP with external sockets disabled. Missing `M`, ambiguous usage or a too-small grant must reject before dispatch. Verify unknown-liability recovery, concurrent-launch exclusion and unchanged native request semantics. Until those checks pass, this remains a proposal rather than a launch-ready fix. Resume the still-unbuilt Gate 2 launch work only after those amended controls pass, within a separately reviewed definition.

Use a new specification/control/source/study identity and output namespace. Keep r010/r012 studies, manifests, source archives and previous decisions immutable. Existing saved outputs may receive compatible later assessments while retaining their recorded generation identity. A greater reservation may change budget stops and coverage; report that operational effect explicitly, and do not pool attempted studies across changed controls without a comparability assessment. No live Phase 2B attempt exists to migrate now.

## Tradeoff and alternative considered

AM-1 avoids changing the scientific procedures or adding provider requests merely to estimate request size. It trades that simplicity for potentially large reservations and replaces a strict input-token-limit claim with a measurable payload limit plus a separately justified financial bound. That tradeoff needs user acceptance. It is not a guarantee that the required input envelope can be documented.

Provider-native token counting was considered and is not the preferred automatic fix: this checkpoint forbids those calls, Anthropic describes counting as an estimate, and OpenAI's documented counting route uses Responses rather than the native Chat Completions grouping contract. Adopting counting would require a different, explicitly authorized amendment with exact-body binding, conservative semantics and endpoint compatibility. Neither an empirical count plus a larger margin nor switching the grouping endpoint silently would satisfy the old policy. [Anthropic counting](https://platform.claude.com/docs/en/build-with-claude/token-counting), [OpenAI counting](https://developers.openai.com/api/docs/guides/token-counting).

The next decision is whether to adopt AM-1 for a separately defined offline control correction. This document supplies no provider-call permission, dollar grant or implemented dispatch path.
