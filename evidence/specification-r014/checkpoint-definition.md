## Live-readiness checkpoint

**Status:** defined, unstarted. This is bounded offline preparation for the first Phase 2B check. The present request authorizes this specification update only. It authorizes no implementation, provider request, human collection or experiment.

### Objective and usable output

Determine whether the existing study can safely request authorization for its first counted live block. Deliver either a tested offline launch candidate with a precise authorization packet, or a source-backed no-go/change-required report identifying the smallest next decision. Neither outcome establishes account access, successful live delivery or actual provider billing.

Keep the checkpoint to one question: **can we defend the exact request, admission, accounting and launch controls for the already frozen first block?** It does not evaluate strategy quality, choose a model, or test recursive improvement.

### Scope and inputs

Inherit the completed revision 0.12 source/study kit, closed in 0.13, without editing it. Preserve the 12 selected development tasks, two repeats, A/B/C procedures, native NoveltyBench v1.1 prompts/schema/arithmetic, optional human sample and both decision policies. The immediate launch target is only the first selected task/repeat-1 block: 21 answer/planning calls, one ranking call, three grouping calls and up to 30 quality-head calls, at most **55 requests**, already included in the study's 1,320 slots.

Keep the pinned models and controls: Sonnet 5.5 adaptive/low with 4,096 total output tokens for answer/plan/rank, Luna grouping with native omitted effort/output-cap fields and a 128,000 output reservation, and Opus 5 adaptive/high with 16,000 output tokens for native quality. Preserve the 8,000 answer/plan/quality and 64,000 rank/group input limits unless a separately reviewed amendment changes them. Availability of documentation is not evidence of access to these models.

The starting gaps are explicit: the byte-length-plus-2,048 estimate is not a certified provider-token bound; grouping cache-write accounting is unsupported; the dispatcher rejects all nonfixture requests; there is no reviewed live runner/launcher; and the transport tests substitute SDK modules rather than exercise actual pinned-SDK HTTP serialization and parsing.

### Work and deliverables

Use two gates within one checkpoint; stop before building a launch route if the first gate fails.

**Gate 1 — a bounded feasibility decision.** Review exact request construction, pinned SDK behavior and dated primary provider documentation. Produce a five-role contract/admission/billing table recording what is proved, assumed, unsupported and still untestable offline. Reconcile input limits with all billable framing/schema expansion, output/thinking, cache reads/writes, context/service/region tiers and any hidden provider defaults. A test corpus or a larger empirical margin alone cannot certify a hard input bound. Do not make an endpoint call to fill an evidence gap.

Current sources reviewed on **2026-10-26, America/Los_Angeles** explain why this gate is substantive. [OpenAI token counting](https://developers.openai.com/api/docs/guides/token-counting) includes request formatting absent from local text tokenization and documents a Responses-format endpoint; that does not establish equivalence to the pinned native Chat Completions grouping body. [Anthropic token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting) accepts structured message inputs; its existence does not certify our offline byte estimate. Neither endpoint is used here.

The [Luna model page](https://developers.openai.com/api/docs/models/gpt-5.6-luna) lists $0.20/M ordinary input, $0.02/M cached input, $1.20/M output and cache writes at 1.25 times ordinary input. Thus $0.25/M is a documented write rate, not a zero-cost category. [OpenAI caching documentation](https://developers.openai.com/api/docs/guides/prompt-caching) distinguishes read/write/input categories. The exact native route's applicable usage fields and default write behavior must still be reconciled with the pinned SDK. Do not transplant a Responses usage example into Chat Completions accounting without evidence. Recheck [Anthropic prices](https://platform.claude.com/docs/en/about-claude/pricing) for the exact Sonnet 5.5 and Opus 5 profiles as well. These are documentation observations, not measured billing outcomes or a frozen replacement cost sheet.

If a supported conservative control cannot be established, stop with the exact missing evidence and one preferred bounded amendment, plus its tradeoff. Possibilities may include separately authorized provider counting with an endpoint-compatibility argument, or a differently justified admission/reservation policy. None is automatically selected or authorized. Do not silently enlarge the allowance, switch API routes/models, change native prompts/effort/output caps, or waive an input limit. A required control/protocol change is reviewed before it is implemented; it receives a new identity and, where relevant, a comparability assessment.

**Gate 2 — a narrow offline launch candidate, only if Gate 1 passes within the unchanged scientific protocol.** Reuse the existing dispatcher, artifact, native adapter and decision modules. Implement only the missing first-block runner and explicit live-launch/preflight seam, with a new source/study identity. The ordinary offline launcher remains network-disabled. The candidate supports only that first block; a full-pilot runner is outside this checkpoint and any missing expansion work is separately scoped after its review. The live route remains unusable without all independently validated prerequisites and a matching future grant; a boolean verification flag is insufficient.

Exercise the actual pinned SDKs with fake keys and local mock HTTP transports, with external sockets disabled. Capture effective request bodies and redacted header identities for all five roles; verify native prompts, schemas, controls and intentional omissions. Test SDK parsing with provider-shaped successful responses, refusals/malformed output, nondefault tiers, cache-write/read usage, missing or inconsistent usage, HTTP rejection, timeout and uncertain delivery. Mock results are labelled fixtures and software evidence only; they cannot become live outcomes or select a real seed.

The launch candidate must validate exact study/source/control identities, role models/endpoints, a grant naming that package and ceilings, and separate first-check versus expansion authority. It permits one request in flight phase-wide, atomic intent before any create, conservative reservation before dispatch, zero automatic retries/fallbacks/repair and no redispatch after unknown delivery. Unknown or unsupported billing retains a liability and halts. Check crash/resume and concurrent-launch behavior; native grouping/head scoring and B-to-C permutation integrity remain unchanged. Every halt produces an inspectable status/accounting report. A partial first block cannot authorize expansion.

Define the future credential/runtime boundary without obtaining credentials here: explicit keys only at authorized launch, presence-only diagnostics, no values in files/logs/arguments, no inherited host environment or home/credential-directory mounts. Restrict dispatch to the two frozen providers and their declared routes, reject ambient base-URL/proxy overrides and redirects, mount code/upstreams read-only and permit writes only to the named new-project run. The offline mock path uses no real key and cannot open an external socket. Account/model authorization and real settings compatibility remain unverified until the counted live check.

The usable handoff consists of:

1. `PHASE2_LIVE_READINESS_REPORT.md`: evidence/assumption table, gate outcomes, exact unresolved issues, limitations and one next decision.
2. A dated cost/reservation sheet and independently checked integer arithmetic, with all billable categories, first-block/full-study scenarios, worst cases and cap-stop consequences. Refresh every applicable price and usage contract before any later grant.
3. If Gate 1 passes: runnable offline preflight/mock trace, the narrow launch candidate, acceptance evidence and a frozen source/control/study bundle. Its launch instructions are review material, not commands to run now. If Gate 1 fails, mark this candidate **not built**, preserve the existing live block and deliver the amendment decision instead.
4. On the successful branch, a first-block authorization packet naming exact tasks/slots, models/settings, controls/source hashes, proposed ceilings, credential/runtime prerequisites, stop/recovery policy and the review required before expansion. It must state `authorized: false` and `live_access_verified: false`. On a no-go, supply only the draft launch conditions and amendment proposal, explicitly not a frozen grant-ready packet, with `launch_candidate_ready: false`.
5. A preservation manifest and requirement-by-requirement acceptance record. Proposed implementation outputs belong under new `runs/phase2-readiness-r014` and `evidence/phase2-readiness-r014` namespaces. Further material changes use a fresh identity; never rewrite r010/r012 manifests or treat the r012 frozen study as generated by new code. No runtime outputs or readiness report are created by this definition update.

### Exclusions

No authenticated provider endpoints, including inference, token counting, model listing, authentication/account probes, cache warming or any nominally free test call. No real credential entry/collection, paid infrastructure, datasets or readers. Public documentation/source research and later offline mocks are within the defined checkpoint; actual execution still needs the user's request to start it.

No Phase 2B first block, expansion, real generation/scoring/reranking, task replacement, held-out inspection, protocol/model/strategy selection, new evaluator, CrPO/MuCE work, Route H or fresh-output human collection, actual Harness² adaptation, generic provider gateway/plugin framework, benchmark sweep, SDK migration or broad dependency upgrade. An essential dependency change becomes a separately recorded compatibility/license/security decision rather than a silent expansion. Reader availability is never a benchmark-readiness gate; later phase definitions remain separate.

There are three distinct outcomes. **Prepared to request authorization:** LR-1 through LR-6 pass for the successful branch; local software is prepared, but no grant, account access or live certification is implied. **Checkpoint complete, change required:** the bounded feasibility investigation ends with adequate evidence for a no-go/amendment decision; a launch candidate remains unbuilt and live dispatch blocked. **Incomplete:** required investigation, evidence or implementation verification is missing. Do not use a partial proof, fixture success or the engineering time limit to claim readiness.

After a successful checkpoint, present the frozen authorization packet. Only a later explicit applicable grant can permit the counted Phase 2B first block, with current prices/access prerequisites rechecked at launch. Its observed results, real provider settings/usage and reconciled liabilities require a separate review before expansion. If that check halts or is incomplete, preserve it and stop; no automatic top-up, additional probe or resampling.
